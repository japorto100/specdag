# Dependency Map Guidance

Use this reference when a feature needs a machine-checkable dependency map for Event-Spec-Driven Development.

A dependency map is not a mindmap and not a runtime engine. It is a small, typed graph that lets humans and agents check what depends on what, what is blocked, what is verified, and which events/contracts connect feature slices.

## When to create `dependency-map.yaml`

Create `dependency-map.yaml` for Level 2+ work when the feature involves any of the following:

- Multiple events, commands, queries, jobs, artifacts, verifiers, approvals, or contracts.
- Cross-feature dependencies through events, contracts, shared artifacts, or approvals.
- Agent workflows where steps must be ordered, verified, replayed, or compared to runtime traces.
- Any change where a missing dependency could cause unsafe execution, stale data, broken sync, or approval bypass.

Do not create a dependency map for isolated Level 0/1 patches unless it clarifies a real dependency risk.

## Local vs global maps

### Local feature map

The local map is authored by humans or agents:

```text
specs/features/<NNN-feature-name>/dependency-map.yaml
```

It describes only the local feature slice:

- the feature intent and expectations;
- local commands, jobs, artifacts, verifiers, and approvals;
- events/contracts produced or consumed by the feature;
- dependencies that matter for implementation, review, verification, or safe execution.

### Generated global map

The global map is generated by `specdag assemble` from all local maps:

```text
specs/_generated/dependency-map.global.json
specs/_generated/dependency-map.global.yaml       # optional
specs/_generated/dependency-map.global.mmd        # optional
specs/_generated/dependency-report.html           # optional
```

Generated global maps and reports are not source of truth. Do not edit them manually. They are review, impact-analysis, visualization, and agent-context artifacts.

Add this comment/header to generated files where possible:

```text
Generated by specdag. Do not edit manually.
Source of truth: specs/features/*/dependency-map.yaml plus domains/, events/, contracts/, foundations/.
```

## Graph kinds

Use `graph.kind` to declare the role of the map:

| Kind | Meaning | Usually executable? |
|---|---|---:|
| `spec_dependency` | Desired dependencies between feature/spec artifacts | No |
| `event_flow` | Causal communication between events, commands, consumers, and state changes | No / partially |
| `agent_run_trace` | Observed runtime trace of an agent run | No, historical |
| `execution_workflow` | A concrete workflow that may be executed by a runtime | Yes |

Do not treat all graph kinds as runtime workflows.

## Topology

Use `graph.topology` to define whether cycles are allowed:

```yaml
graph:
  id: research-import
  kind: spec_dependency
  topology: dag
  status: draft
```

| Topology | Meaning | Cycle behavior |
|---|---|---|
| `dag` | Workflow, derivation, verification, task, or execution graph | cycles are errors |
| `graph` | Domain relation, feedback loop, non-execution causal map | cycles are allowed |

Default to `dag` unless a cycle is intentional and explained.

## Node ID conventions

Use stable, namespaced IDs.

Feature-local nodes should include a feature prefix:

```yaml
- id: feature.research-import.intent.main
  type: intent
  title: "User can import research documents"
```

Durable cross-feature nodes should use domain/event/contract prefixes:

```yaml
- id: event.document.uploaded
  type: event
  title: "document.uploaded"
  ref: "specs/events/document/document.uploaded.md"
  owner: "document"
  status: accepted
```

Recommended prefixes:

| Prefix | Use for |
|---|---|
| `feature.<feature>.intent.*` | feature-local intent nodes |
| `feature.<feature>.expectation.*` | feature-local expectations |
| `feature.<feature>.job.*` | feature-local jobs |
| `event.<domain>.<past-tense-verb>` | durable events |
| `contract.<domain>.<name>` | durable API/event/auth/data contracts |
| `artifact.<domain>.<name>` | durable artifacts |
| `verifier.<domain>.<name>` | reusable verifiers |
| `approval.<domain>.<name>` | reusable approval gates |

Avoid generic IDs such as `intent.main`, `event.created`, `job.process`, or `approval.required`.

## Node fields

```yaml
nodes:
  - id: event.document.uploaded
    type: event
    title: "document.uploaded"
    ref: "specs/events/document/document.uploaded.md"
    owner: "document"
    status: accepted
```

| Field | Required | Meaning |
|---|---:|---|
| `id` | yes | stable graph identity |
| `type` | yes | allowed node type |
| `title` | yes | human-readable label |
| `ref` | no | path to source spec, event, contract, policy, artifact, or evidence |
| `owner` | no | owning domain/team/module |
| `status` | no | `draft`, `accepted`, or `superseded` |

## Edge fields

```yaml
edges:
  - from: event.document.uploaded
    to: feature.research-import.job.extract-text
    type: triggers
    condition: "file.mime_type in supported_types"
    required: true
```

| Field | Required | Meaning |
|---|---:|---|
| `from` | yes | source node ID |
| `to` | yes | target node ID |
| `type` | yes | allowed edge relationship |
| `condition` | no | condition under which the edge applies |
| `required` | no | whether this dependency is mandatory |

## Allowed node types

- `intent`
- `expectation`
- `event`
- `command`
- `query`
- `contract`
- `job`
- `artifact`
- `verifier`
- `approval`

## Allowed edge types

- `defines_success_for` — intent -> expectation
- `triggers` — event -> job/command
- `produces` — job -> artifact/event
- `consumes` — job/command -> artifact/event
- `verified_by` — artifact -> verifier
- `verifies` — verifier -> expectation
- `requires_approval` — job/event -> approval

## Generated review artifacts

Generated reports are helpful for humans but are not authoritative specs.

Recommended outputs:

```text
specs/_generated/dependency-map.global.json
specs/_generated/dependency-map.global.mmd
specs/_generated/dependency-report.html
```

A useful HTML report should show:

- graph metadata;
- validation warnings and errors;
- critical path;
- blockers;
- approval gates;
- verification coverage;
- orphan nodes;
- event/contract references;
- Mermaid diagram or Mermaid source;
- raw JSON/YAML links.

## Test fixtures

Keep mock maps outside real specs:

```text
testdata/
  valid/
    upload-feature.yaml
    processing-feature.yaml
    notifications-feature.yaml
  invalid/
    cyclic-feature.yaml
    duplicate-node-conflict.yaml
    missing-edge-target.yaml
    invalid-edge-type.yaml
```

Do not place test or mock maps in `specs/features/` unless they are real product specs.

## Common mistakes

- Forcing every small feature to have a map.
- Editing generated global JSON or HTML by hand.
- Treating HTML/Mermaid output as source of truth.
- Using generic node IDs that collide across features.
- Hiding durable events/contracts inside feature-local names.
- Forcing feedback loops or domain relationship graphs into a DAG.
- Treating `agent_run_trace` as the desired spec rather than observed runtime evidence.
